Using OpenFOAM does not make simulations public or expose proprietary data. OpenFOAM is simply an open-source CFD solver, not a hosted service. It runs locally on your servers or infrastructure, meaning all simulation inputs, meshes, and results remain inside your system.
The open-source nature affects code transparency, not data ownership or privacy.
￼
1. How OpenFOAM Actually Runs
OpenFOAM is typically executed as a command-line solver on a machine you control.
Typical workflow inside your platform:
User uploads geometry ↓ Nereus backend generates CFD case ↓ OpenFOAM runs simulation locally in container ↓ Results written to storage ↓ Dashboard visualizes results
All files exist inside your infrastructure.
Nothing is sent externally.
￼
2. What “Open Source” Means in This Context
Open source means:
* You can inspect and modify the solver code.
* The solver algorithms are public.
It does not mean:
* simulations are shared
* user data is exposed
* results are published
This is similar to how companies use:
* Linux internally
* PostgreSQL for proprietary systems
Even though those tools are open source, the data inside them remains private.

How could we reduce daysto hours in the simulation run time
Reducing CFD simulation time from days to hours is possible, but it requires optimization across four areas:
1. Compute architecture
2. Solver configuration
3. Mesh complexity
4. Modeling approach
Engineering organizations already achieve large reductions in runtime when using optimized setups around solvers such as OpenFOAM and HPC clusters.
Below are the main strategies that make the largest difference.
￼
1. Parallel Computing (Largest Immediate Impact)
CFD simulations are naturally parallelizable.
Instead of running on a single CPU, the simulation runs across many cores simultaneously.
OpenFOAM supports MPI parallelization using libraries like:
* Open MPI
Example:
Single CPU → 48 hours 32 CPU cores → 3–4 hours 128 CPU cores → <1 hour
Simulations are split into domain partitions, with each core solving part of the mesh.
This is the most common technique used in engineering HPC clusters.
￼
2. GPU Acceleration
Traditional CFD solvers are CPU-based, but GPUs can massively accelerate certain computations.
GPU-enabled solvers can reduce runtime by 10–50× depending on the case.
Examples include:
* NVIDIA CUDA
* AMGX
Some CFD implementations integrate CUDA-based solvers for faster matrix operations.
￼
3. Mesh Optimization
The mesh determines the number of cells the solver must compute.
Simulation time scales roughly with cell count.
Example:
10 million cells → hours 100 million cells → days
Ways to reduce cell count:
Adaptive Mesh Refinement
Only refine mesh where necessary (around hydrofoils).
OpenFOAM includes tools like:
* snappyHexMesh
This allows:
* coarse mesh in open water
* fine mesh near foil surfaces
￼
4. Simplified Physics Models
High fidelity simulations often use expensive models such as:
* Large Eddy Simulation (LES)
These can take extremely long.
Faster alternatives:
* RANS turbulence models
* steady-state simulations
Many early design simulations use simplified models to speed iteration.
￼
5. Smart Initial Conditions
Starting the solver from scratch increases convergence time.
Instead:
* reuse previous simulation states
* warm-start the solver
This can reduce simulation time significantly during design iterations.
￼
6. Reduced Domain Simulation
Often the entire ocean environment does not need to be simulated.
Instead:
simulate a localized fluid domain around the hydrofoil.
Example:
Full ocean domain → expensive Localized domain → far faster
Boundary conditions approximate the external environment.
￼
7. Surrogate Models (Huge Speed Gains)
Once several CFD simulations exist, machine learning models can approximate results.
Approach:
1. Run high-fidelity simulations
2. Train surrogate model

How could we reduce daysto hours in the simulation run time
Reducing CFD simulation time from days to hours is possible, but it requires optimization across four areas:
1. Compute architecture
2. Solver configuration
3. Mesh complexity
4. Modeling approach
Engineering organizations already achieve large reductions in runtime when using optimized setups around solvers such as OpenFOAM and HPC clusters.
Below are the main strategies that make the largest difference.
￼
1. Parallel Computing (Largest Immediate Impact)
CFD simulations are naturally parallelizable.
Instead of running on a single CPU, the simulation runs across many cores simultaneously.
OpenFOAM supports MPI parallelization using libraries like:
* Open MPI
Example:
Single CPU → 48 hours 32 CPU cores → 3–4 hours 128 CPU cores → <1 hour
Simulations are split into domain partitions, with each core solving part of the mesh.
This is the most common technique used in engineering HPC clusters.
￼
2. GPU Acceleration
Traditional CFD solvers are CPU-based, but GPUs can massively accelerate certain computations.
GPU-enabled solvers can reduce runtime by 10–50× depending on the case.
Examples include:
* NVIDIA CUDA
* AMGX
Some CFD implementations integrate CUDA-based solvers for faster matrix operations.
￼
3. Mesh Optimization
The mesh determines the number of cells the solver must compute.
Simulation time scales roughly with cell count.
Example:
10 million cells → hours 100 million cells → days
Ways to reduce cell count:
Adaptive Mesh Refinement
Only refine mesh where necessary (around hydrofoils).
OpenFOAM includes tools like:
* snappyHexMesh
This allows:
* coarse mesh in open water
* fine mesh near foil surfaces
￼
4. Simplified Physics Models
High fidelity simulations often use expensive models such as:
* Large Eddy Simulation (LES)
These can take extremely long.
Faster alternatives:
* RANS turbulence models
* steady-state simulations
Many early design simulations use simplified models to speed iteration.
￼
5. Smart Initial Conditions
Starting the solver from scratch increases convergence time.
Instead:
* reuse previous simulation states
* warm-start the solver
This can reduce simulation time significantly during design iterations.
￼
6. Reduced Domain Simulation
Often the entire ocean environment does not need to be simulated.
Instead:
simulate a localized fluid domain around the hydrofoil.
Example:
Full ocean domain → expensive Localized domain → far faster
Boundary conditions approximate the external environment.
￼
7. Surrogate Models (Huge Speed Gains)
Once several CFD simulations exist, machine learning models can approximate results.
Approach:
1. Run high-fidelity simulations
2. Train surrogate model
3. Predict results instantly
Python tools such as:
* TensorFlow
* PyTorch
can learn relationships between:
* foil geometry
* velocity
* lift/drag outputs
Predictions then take seconds instead of hours.
￼
8. Simulation Caching
Many engineers rerun similar simulations.
Example:
same hydrofoil same speed slightly different wave height
Instead of recomputing everything, reuse cached flow fields.
￼
9. Automated Design Optimization
Instead of running hundreds of separate simulations sequentially, run them in parallel batches.
Example:
100 simulations sequentially → days 100 simulations on cluster → hours
This requires orchestration systems running many solver containers simultaneously.
￼
10. Precomputed Ocean Models
Instead of simulating waves during every run, use precomputed wave fields.
Ocean models like:
* SWAN
can generate wave environments once, then reuse them across many simulations.
￼
Realistic Performance Targets
With proper optimization:
Setup	Typical runtime
Single workstation	12–48 hours
Small cluster	3–8 hours
Large HPC cluster	30–90 minutes
￼
What Nereus Could Do Differently
The biggest opportunity is automation + compute orchestration.
Most CFD engineers lose time on:
* mesh setup
* solver configuration
* cluster setup
If the platform automatically:
* generates optimal meshes
* parallelizes jobs
* selects turbulence models
* runs simulations across many nodes
engineers could reduce iteration cycles dramatically.
￼
Key Insight
The main goal should not be making the physics solver faster, but rather:
maximizing compute parallelism and minimizing unnecessary simulation complexity.
That combination is what turns multi-day simulations into multi-hour workflows.
